Verified on 2026-11-16 for the initial scaffold:

| Component | Pinned version or requirement | Compatibility evidence |
| --- | --- | --- |
| Target framework | `net10.0` | Microsoft Azure Functions isolated-worker guide lists .NET 10 for Functions 4.x |

The Functions app uses the isolated worker model, with the Functions build SDK
resolved through the scoped `msbuild-sdks` entry in `global.json`. NuGet package
versions are centrally managed by this solution's `Directory.Packages.props`;
analyzers are configured by its `Directory.Build.props`. Neither file applies
to the existing demos.

The `global.json` is at the PizzaOps solution root, and all service projects
are beneath it. A future AZD service configured with one of those project
directories will resolve the SDK from this scoped file even when AZD itself is
started at the repository root. The current root `azure.yaml` has no PizzaOps
service entries, so AZD packaging is intentionally not configured or claimed
as tested by this task.

The isolated-worker guide documents `Azure.Functions.Sdk` 1.0.0 and Worker
2.52.0 in its .NET 10 project configuration. The MCP binding documentation
requires SDK 1.0.0 or later and Worker 2.1.0 or later. Release 1.6.0 is the
latest release available in the official MCP extension repository at the
verification date, and restore/build succeeded with this package set.

The linked Microsoft Learn sample currently pins Worker 2.52.0 and MCP
extension 1.5.0, and uses `Microsoft.NET.Sdk` with
`Microsoft.Azure.Functions.Worker.Sdk` 2.0.7. This scaffold follows the newer
isolated-worker guide's `Azure.Functions.Sdk` project-SDK recommendation and
the MCP extension's 1.6.0 release. The sample also references the prerelease
`Microsoft.Azure.Functions.Worker.Extensions.Mcp.Sdk` package; this empty host
does not add it before any MCP trigger source is implemented, so its need is a
compatibility gate for the trigger task rather than an assumed dependency.

## Task 05 protocol gate: blocked

On 2026-11-16, the existing Functions host's generated restore assets resolved
`Microsoft.Azure.Functions.Extensions.Mcp` 1.6.0 and its dependency
`ModelContextProtocol` 0.4.0-preview.3. The latter's
[source at the package commit](https://github.com/modelcontextprotocol/csharp-sdk/blob/2da929914c2d7becbab0a51d1bda171aec4ce9e8/src/ModelContextProtocol.Core/McpSessionHandler.cs)
lists `2025-06-18` as its latest supported protocol revision, alongside
`2025-03-26` and `2024-11-05`; it does not list the plan's `2026-07-28` target.
On 2026-11-16 the user accepted the older Functions protocol revision for now.
With Core Tools 4.16.0 (Functions runtime
4.1054.250.26428), Azurite 3.35.0, and a reset in-memory kitchen:

- The official C# client `ModelContextProtocol` 2.1.0 negotiated `2025-06-18`
  over Streamable HTTP and called both read tools. The opt-in
  `McpReadToolsTests` asserts the schema, seeded status, recipes, and errors.
- MCP Inspector 2.14.0 in legacy mode listed and called both tools. Its strict
  schema check passed. In pinned modern mode it failed negotiation: the server
  did not offer `2026-07-28` through `server/discover`.
- Copilot CLI 1.0.106, configured with a temporary local HTTP server entry,
  discovered two tools and successfully called both. Its negotiated protocol
  revision was not captured. This CLI run does not establish compatibility of
  the intended VS Code presenter configuration.

The actual schemas contain `type: object`, `properties`, and `required`.
Status has no properties and an empty required array; recipe has one required
string property `pizza_type`. Neither schema advertises `additionalProperties`
or a recipe enum. The extension returns a text content block containing the
application JSON envelope. A missing required recipe argument is a protocol
error. The binding coerces a numeric argument to a string, so the adapter
checks the original invocation argument and returns `INVALID_ARGUMENT`.
Initially, stopping Azurite exposed an aggregate retry exception instead of the
application envelope. After mapping exhausted read retries to storage failure,
Inspector returned `success: false` and `code: STORAGE_UNAVAILABLE` in a JSON
text content block. A focused unit test also covers exhausted retries for oven
and event reads.

Task 05 remains blocked until the intended VS Code presenter configuration is
verified. An attempted UI interaction was interrupted by active user input, so
no VS Code discovery or call is claimed. Local execution does not prove deployed
System-key security.

`Directory.Solution.targets` includes the documented recursive
`GenerateFunctionsExtensionProject` restore hook. This ensures restoring the
solution generates the Functions extension project before build rather than
triggering AZFW0108's restore-during-build fallback.

Run the scaffolded test projects from the solution directory with
`dotnet test .\PizzaOps.sln --no-build`. They currently contain no behavior
tests, so this command confirms runner discovery only and is not coverage
evidence.

## Task 07 local four-tool and bake verification

On 2026-11-16 the same pinned host and official C# client negotiated
`2025-06-18` and passed all three opt-in `FullyQualifiedName~Mcp` tests against
local Azurite. The real `tools/list` catalog contains exactly
`bake_test_pizza`, `get_ovens_status`, `get_pizza_recipe`, and
`set_oven_temperature`. Bake has exactly two required string properties:
`oven_id` and `pizza_type`. Its description explicitly discloses event writes.
As with the other tools, the return value is application JSON in a text content
block, not MCP structured content.

The extension advertises generic resource/prompt support. Actual
`resources/list`, `resources/templates/list`, and `prompts/list` return empty
catalogs; no resources, templates, prompts, or admin tools are registered.
The adapter checks original invocation arguments because the extension can
coerce non-string values and does not advertise `additionalProperties: false`.

The wire tests verify a completed BURNT observation at 450 C, repair to PASS
at 320 C, both inclusive Margherita tolerance boundaries and adjacent failures,
normalized and missing/invalid arguments, unique repeated events, and exact
oven entity/ETag/timestamp preservation. Temporarily deleting the local events
table verifies that a completed bake remains `TEST_COMPLETED` with its observed
result, `event_recorded: false`, and an explicit warning. Reset restores the
local tables and canonical kitchen afterward. Focused unit tests additionally
verify unknown event-write outcomes and cancellation without replay.

Validation commands, from the solution directory (with Azurite, a freshly
reset kitchen, and the Functions host running for the MCP tests):

```powershell
dotnet test .\tests\PizzaOps.UnitTests\PizzaOps.UnitTests.csproj --no-restore --filter "FullyQualifiedName~Bake|FullyQualifiedName~TemperatureChangeServiceTests|FullyQualifiedName~TableReadFailureTests|FullyQualifiedName~ValidationAndContractsTests"
$env:PIZZAOPS_MCP_TESTS = "true"
dotnet test .\tests\PizzaOps.IntegrationTests\PizzaOps.IntegrationTests.csproj --no-restore --filter "FullyQualifiedName~Mcp"
```

This evidence is local only. It does not resolve Task 05's intended VS Code
presenter gate, prove deployed System-key security, or claim support for
protocol `2026-07-28`.

## Local validation boundary

`dotnet restore`, `dotnet build`, `dotnet test`, and `dotnet format` operate
without Azure authentication and do not create or modify cloud resources.
Functions Core Tools are needed only to start a local Functions host. Any
future Azure deployment or resource provisioning must be an explicit, separate
operation.
